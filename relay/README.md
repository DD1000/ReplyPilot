# Reply Pilot relay

**0.12.0 — Train Autopilot.** `POST /persona-train` accepts one contact's most recent texts (1–1,000 `me`/`them`/`autopilot` turns, each up to 2,000 characters, 300,000 total; no names, numbers or ids) and returns a bounded persona (`writingStyle`, `relationship`, `context`, `avoid`) plus up to 30 indexes of the owner's own messages to use as examples. It uses `OPENAI_TRAINING_MODEL` (default `gpt-6-astra`, reasoning effort medium, 150-second limit) and retries once with `OPENAI_MODEL` when the key can't use the training model. Draft, Autopilot and media requests accept an optional `persona` (the phone's stored persona with up to 30 `{incoming,reply}` examples) validated on every request. Authenticated `/health` adds `personaVersion:1`, `trainingModel` and `trainingModelAvailable`, checked with a free model-metadata request cached for 10 minutes. Nothing is stored: no conversation database, `store:false`, and the persona lives only on the phone. `/history-analysis` and `historyMemory` remain for 0.11.x phones.


## 0.11.0 current protocol

The deployed service supports `autopilotVersion:1` and `historyAnalysisVersion:1` at authenticated `/health`. Existing older client contracts remain compatible. Current phones no longer invoke `/train` or provide practice/meaning examples.

`POST /draft` with `autopilot:true` uses a separate short-reply schema: decision, reason, body, attentionNeeded, attentionReason. Valid new messages get a reply, with a safe noncommittal deferral for planning/unknown facts instead of the old approval hold. Readiness, authentication, rate limits and exact location-context rules remain. Phone-side source and permission validation owns actual SMS sending. Provider failures can yield a marked safe deferral; that is not evidence the provider answered successfully.

`POST /history-analysis` accepts requestId, previous `{writingStyle,historicalContext}`, up to40 `{speaker,text,continuation}` fragments, and finalBatch. Each fragment is at most4000characters, the batch at most48000text characters and262144HTTP bytes. It returns `{memory:{writingStyle,historicalContext}}`, each field at most1800characters. Missing/malformed summaries fail; failed requests may retry the same ID, while successful results deduplicate for five minutes. No names, recipient addresses or local thread IDs are accepted as request fields. Text itself can contain private information, as authorized by the owner.

Later drafts include optional bounded `historyMemory`. It is fallible historical context, not current facts, consent or model training. The phone owns encrypted per-contact storage and readiness checkpoints. The relay uses no conversation database, no tools, store:false and the existing configured model. Initial analysis shares the existing20/minute,200/day and2in-flight limits; large histories can pause and require retry after the limit resets. No limits or credentials were changed.

## Connect it

1. Choose a host that runs a Node service behind HTTPS. Railway is supported by the included Dockerfile and `railway.json`; use **relay/** as the deployment root. Keep one running replica and disable Serverless/app sleeping for the requested always-on setup. The HTTPS address must be an origin with no path, such as `https://your-service.up.railway.app`.
2. Generate the phone credential locally from this directory: `node pair.mjs https://YOUR-SERVICE-DOMAIN`. It writes a random token and a phone pairing code under `../.local-secrets/` with owner-only permissions. It prints paths, not secrets. Rerunning preserves the same token; remove that local token file only when intentionally rotating it.
3. In the host’s private Variables/Secrets settings, enter `OPENAI_API_KEY` and `REPLY_PILOT_TOKEN`. Use the contents of `phone-token.txt` for the latter. Do not put the OpenAI key in the APK, source, chat, screenshots or public deployment configuration. A dedicated OpenAI project/key is recommended. The key needs Responses API write permission and access to the selected model. Add API billing separately from any ChatGPT subscription.
4. Deploy. The Docker image listens on the host-provided `PORT` (8781 otherwise). Its plain HTTP listener belongs behind the host’s TLS proxy; never expose it directly. `GET /status` is an unauthenticated liveness check only and returns no configuration. Protect `/health` and `/draft` with the phone token.
5. On the Pixel, open Reply Pilot 0.7.18 → Settings → Phone pairing code, paste `phone-pairing.txt`, and save. The code is private: possession permits paid draft requests. **Check connection** verifies the service and whether a key is configured; it does not validate OpenAI access or billing. Use **Try AI → OpenAI → Generate test reply** for the real end-to-end check.

In Railway, set private values in the service’s Variables tab, then deploy the staged changes. Generate a public domain under Networking. Do not enable request-body/header logging or caching at an added proxy. The Railway integration is connected. The private project is Reply Pilot; its prepared HTTPS endpoint is https://reply-pilot-api-production.up.railway.app. The local-code upload completed using the separate Railway CLI sign-in. The phone credential has already been configured; do not replace it unless rotating access intentionally.

## Configuration

| Variable | Purpose |
| --- | --- |
| `OPENAI_API_KEY` | Server-only OpenAI key; never returned to the phone. |
| `REPLY_PILOT_TOKEN` | Random 32–128 character base64url phone credential. Generate with `pair.mjs`. |
| `OPENAI_MODEL` | Reply model. Defaults to `gpt-6-sol`. An alternative must support Responses, strict structured outputs and `reasoning.effort: none`. |
| `OPENAI_TRAINING_MODEL` | Train Autopilot model. Defaults to `gpt-6-astra`; falls back to `OPENAI_MODEL` if the key can't use it. |
| `PORT` | Host-provided listening port, otherwise 8781. |
| `HOST` | Docker uses `0.0.0.0`; standalone defaults to loopback. |
| `TRUST_TLS_PROXY` | Docker uses `yes` because its production endpoint must sit behind trusted HTTPS termination. |
| `OPENAI_KEY_FILE`, `REPLY_PILOT_TOKEN_FILE` | Optional protected secret-file alternatives to environment values. |
| `TLS_KEY_FILE`, `TLS_CERT_FILE` | Optional direct TLS; the phone requires a normally trusted certificate matching the host. |

Local service-boundary tests run on loopback HTTP and never contact OpenAI: `node --test *.test.mjs`. The phone refuses plain HTTP.

Version 0.7.9 requires the history service update for 50-message context. The newer safety protocol accepts older request shapes but returns no reply when automatic eligibility is missing; an updated phone is required to assert eligibility or explicitly request a manual/test draft. Reading/preparing history on the phone makes no model request; selected context is included only when generating a draft. This is request context, not fine-tuning or a persistent provider memory.

## Request contract and data handling

- Authenticated `GET /health`: key-configured flag, model, `contextLimit:50`, `contextVersion:2`, `replyDecisionVersion:1`, `replySafetyVersion:1`, `planSafetyVersion:1`, `personalizationVersion:1`, `locationVersion:1`, `girlfriendModeVersion:1`, `attentionActionsVersion:1`, `contactHumorVersion:1`, `mediaAnalysisVersion:1` and `approvedLearningVersion:1`; no credential value.
- Authenticated `POST /draft`: request ID, one to fifty `{speaker:"me"|"them",text}` turns, relationship context (up to 4,000 characters, including the optional 1,500-character Relationship Dynamic, 2,000-character Important Details and fixed preset guidance), per-person samples/imported Me/Them chat logs (8,000), optional six sent-style examples (220 each), tone, and optional booleans `automatic` and `automationReady`. Use `automatic:true` for background requests and `false` for explicitly requested manual/test drafts. Omitted `automatic` defaults to `true` because older phones may automatically send the result. Automatic requests require `automationReady:true`, otherwise they return `insufficient_history` without an OpenAI call. The phone computes eligibility from that person's SMS and imported logs; explicit manual/test drafts bypass only this history gate. The latest turn must be incoming. Unknown fields, including names, numbers, requested models and tools, are stripped.
- Successful results include `decision`, `reason`, `body`, `engine` and `elapsedMs`. A reply is `{decision:"reply",reason:"reply_needed",body:"..."}`. Silence is `{decision:"no_reply",reason:"conversation_complete"|"repeated_reply"|"needs_review"|"insufficient_history"|"plans_need_input",body:""}`. The phone must never schedule or send a no-reply result. Older phones that do not understand decisions still receive an empty body, which their draft validation rejects.
- Invitations, availability, scheduling, confirmations and changed plans need the owner's input. Common cases return `plans_need_input` before an OpenAI request; model instructions handle contextual cases. Both layers consider all consecutive incoming messages since the latest outgoing message, so “dinner” / “tomorrow?” / “thanks” stays held. Generated availability claims, invitations and commitments are also held. This applies to explicit AI drafts as well as automatic mode; manually typed SMS remains available. The phone owns alerts and persistent holds until the owner replies. Historical anecdotes and unrelated topics remain contextual. Pattern matching and model instructions reduce mistakes but cannot guarantee detection of every phrasing.
- Clear requests for code, tutorials, essays, homework answers or instruction overrides return `needs_review` without an OpenAI call in both automatic and manual/test modes. Ordinary mentions of Java, programming or an access code are left to contextual judgment. Model replies over 360 characters or 60 whitespace-separated words, containing fenced code, or containing at least three list items return an empty `needs_review` result; the service never truncates an unsuitable reply into a sendable draft. Other uncertainty, missing personal answers and private credentials are addressed by model instructions, not a deterministic guarantee. Owners can still write their own messages in the app.
- Optional `engagement` is `natural` (legacy default), `always_reply`, `keep_going` or `girlfriend`. In natural mode, eligible whole-message acknowledgments such as “Ok,” “Thanks,” or a thumbs-up immediately following an owner turn are resolved without an OpenAI call. Always reply allows one ordinary acknowledgment response; Keep conversation going may also ask one relevant, natural follow-up. Higher-engagement modes stop subsequent acknowledgment-only messages after a sent response until a substantive incoming message resets the allowance. Questions and substantive clauses still receive contextual judgment. None of these preferences bypasses planning, readiness, recipient boundaries or safety holds. Automatic generated replies that duplicate an owner turn after case/spacing/apostrophe/trailing-punctuation normalization are suppressed when at least 20 characters and more than three words long. Short answers and explicit manual/test requests bypass these acknowledgment/duplicate checks; the model assesses other completed conversations and repeated promises. Limits and request-ID caching also apply to no-reply results.
- Girlfriend Autopilot (`girlfriend`) asks for warm, brief owner-grounded replies and at most one relevant follow-up. It cannot invent first-person experiences, feelings or promises; relationship conflict or uncertainty about personal intentions calls for `needs_review`, while concrete plans retain `plans_need_input`. A current bedtime/goodnight or stop-contacting request returns `conversation_complete` before drafting, even if that same message also mentions plans. Negated, historical and quoted statements are excluded from the direct bedtime check. In an unanswered sequence, later acknowledgment/emoji reactions keep it paused; a later substantive incoming turn can resume. The phone owns the durable per-contact pause across requests. These are safeguards and prompting rules, not a guarantee of interpreting every relationship nuance correctly.
- Optional `ownerInterpretation` accepts only `"joke"`; omission retains ordinary behavior. The phone supplies it only after the owner's explicit Joke action. It asks the model to reconsider humorous intent in the current unanswered sequence, without changing global style or retaining a hint for later requests. It bypasses only deterministic incoming planning/assistant-task wording checks; actual plans, uncertain personal facts, authenticity, conflict and boundaries remain subject to the model's existing holds. Generated commitments and unsuitable output remain blocked. Bedtime, history eligibility, duplicate checks, location consent context/freshness and exact-label restrictions remain enforced. Hinted location questions use contextual drafting instead of the simple label template. The hint participates in request-ID caching; adding/removing it requires a new ID. Incoming text or profile examples cannot activate it. The service returns normal decisions only and neither clears a phone planning hold nor grants sending approval.
- Optional `personality` accepts only string fields `about` (1,200 characters), `voice` (800), `humor` (800), `avoid` (800) and `examples` (2,400), totaling at most 6,000. Missing fields are empty. The global profile supports every tone, while `Myself (beta)` emphasizes the owner's voice and humor examples. Profile text stays untrusted input, cannot override rules, and supplies no proof of current facts, plans or whereabouts. Me/Them examples imitate only Me. Humor remains contextual, respects boundaries and serious situations, and is not forced when intent is unclear. This is per-request context, not model training.
- Optional `approvedExamples` defaults to `[]` on both endpoints. It accepts at most twelve objects with exactly nonempty string `incoming` (600 characters) and `reply` (360 characters). The phone selects final, successfully sent replies the owner explicitly reviewed, excluding automatic messages and unsent drafts. The relay validates shape but cannot independently verify the phone's approval evidence. Prompt guidance prefers these reply fields for the owner's writing style; incoming fields provide context only. Pairs remain untrusted per-contact data, cannot authorize new facts or commitments, and do not count as automatic-readiness evidence. They participate in cache identity and are not retained as model training.
- Current phones send `styleMode:"learned"`: the relay uses actual/approved/practice writing and per-contact notes without a tone, relationship-category, numeric humor or separate inside-jokes preset. Legacy tone/humor/joke values are normalized away and omitted from provider input in this mode. Notes remain bounded untrusted user input, never prompt instructions, live-location evidence, availability, consent or authorization to make plans. The request cache distinguishes learned mode from legacy mode. `/health` advertises `contactGuidanceVersion:1`.
- For older clients without `styleMode`, optional flat `humorLevel` is a numeric integer: `0` Light (PG-13), `1` Playful, `2` Sarcastic, `3` Edgy or `4` Extreme; omission defaults to `0`. Strings, nulls, fractions and out-of-range numbers are rejected. Optional `insideJokes` is a string of at most 2,000 characters, empty when omitted; nonstrings/nulls are rejected. Both fields belong to this contact and the request-cache identity. Notes are preserved in JSON input as untrusted context, never interpolated into instructions or shared across requests. The fixed prompt treats intensity as a ceiling, not a quota, and lets the contact ceiling cap stronger global humor preferences in every tone, including Myself. Inside jokes may inspire fitting callbacks but cannot invent memories or expose notes wholesale. Serious topics, current mood, owner avoid notes, recipient boundaries and consent narrow every level. Extreme permits welcome adult innuendo and strong language, never graphic sexual content/erotica, hate/slurs, coercive humor or sexual jokes about minors; sexual-context humor stays clean when someone is known or reasonably suspected to be a minor, and the selected level never overrides age or consent boundaries. Humor and Joke clarification cannot override planning, bedtime, privacy, no-reply or output limits. These tone/content boundaries use model instructions and are not guaranteed by a keyword filter.
- Optional `locationContext` has exactly `label`, `capturedAt` and `expiresAt`; timestamps are integer epoch milliseconds. The phone supplies it only for an opted-in contact asking a current whereabouts/home question. The relay independently detects common questions and returns `needs_review` when context is missing or stale; indirect phrasings also receive explicit no-guessing model guidance. Capture age and total lifetime are at most 25 minutes, future capture tolerance is 60 seconds, and expiry must still be in the future. Allowed coarse labels are `at home`, `near PLACE in CITY`, `near CITY`, `near PLACE`, or legacy `in CITY`; no coordinates, street address, control characters or unknown fields are accepted. Model input omits irrelevant location context. Location replies must contain only that exact label, optionally an “I'm”/“I am”/“im” prefix and terminal punctuation. Cached and in-flight results recheck expiry. The phone separately enforces contact consent, provenance and freshness before scheduling or sending. Planning still requires the owner; neither profile nor history authorizes guessing a location.
- A whole simple whereabouts question such as “Where are you right now?” can return `I'm <approved label>.` without a model call. Every unanswered message must be a pure location question, or the complete split sequence must form one. Planning, readiness, unsuitable-request and duplicate-response checks still apply, as do output limits, expiry and request caching. Extra requests, conditions or acknowledgments take the contextual model path with the same exact-label output restriction; no other fact is added to the template.
- The phone excludes other conversations and unsent/failed texts. Earlier historical turns are bounded to 600 characters; every turn in the unanswered incoming sequence can contain up to 1,600 characters. The latest 50 combine incoming and actually sent messages; only the owner's sent turns guide learned style. When `matchStyle:false`, at most eight immediate turns or the full unanswered incoming sequence (up to 50 turns) are accepted, and extracted style examples are ignored; explicit profile samples remain. Oversized messages, sequences or HTTP payloads require owner input rather than silently truncating the message being answered.
- Authenticated `POST /media-analysis` accepts the same per-contact profile, humor and approved-writing fields, plus `mediaType:"image"|"video"`, optional `caption` (1,600 characters), optional `mediaLimitations` (360 characters), and one to three exact `{jpegBase64,label}` objects. `jpegBase64` is canonical bare base64 of a JPEG, not a URL or data URL; `label` is a nonempty string up to 80 characters. Each decoded JPEG is at most 153,600 bytes and 1,024 pixels per edge, with at most 460,800 decoded bytes total. JPEG markers, segment framing and dimensions are checked; the service does not locally decode compressed pixels. The HTTP JSON envelope is at most 1 MiB, while `/draft` keeps its 256 KiB limit. Media history may be empty or end with an owner turn; ordinary history matching/bounds still apply. `automatic` must be absent or false. The phone handles unavailable media locally instead of requesting analysis with no images.
- Media results contain `summary` (up to 600 characters), `intent` (up to 360, prefixed “Possible intent:”), `confidence:"low"|"medium"|"high"`, `limitation` (up to 360), `suggestion` (up to 360 characters and 60 words), `reason`, `reviewOnly:true`, `engine` and `elapsedMs`. Video limitations always disclose sampled still frames and no audio/full-motion analysis. All six model fields are required; invalid or contradictory output, refusal and incomplete responses are rejected. Overlong/fenced/list suggestions are held without truncation. Caption/history plans, stopping requests and unknown-location questions can still receive useful neutral analysis but never a sendable suggestion; generated commitments and common whereabouts claims are held too. Visual planning and other unknown facts rely on model safety decisions. Media suggestions remain review-only and never create approval evidence.
- Media input uses inline Responses `input_image` items at the fixed OpenAI endpoint. No remote media URL is fetched. Image-visible text, labels and limitation notes remain untrusted input. Prompt rules forbid identifying faces, inferring private traits/health/relationships from appearance, mind-reading, disclosing credentials or inferring current whereabouts. Media input strips `locationContext` even when supplied; permission for a text-based location reply does not authorize visual location inference. Visual interpretation, privacy-sensitive semantic detection and confidence are not guaranteed by deterministic validation. The same authentication, rate/daily/in-flight limits and five-minute request-ID cache apply across both endpoints, including endpoint identity, image bytes and approved examples.
- Fixed OpenAI Responses endpoint; no redirects or tools, `store:false`, maximum 320 output tokens for drafts and 700 for media analysis. Strict `text.format` JSON schemas require every declared field and reject extras. Server validation also checks decision/reason/body consistency. A refusal, incomplete response, malformed object or contradictory decision never becomes a usable draft; empty bodies are accepted only for valid no-reply decisions. Instructions draft as the phone owner, keep notes private and forbid invented expertise, commitments or external actions. Imported logs remain untrusted input for voice only, never current facts or instructions. Contextual judgment and reply quality still require device and conversation testing.
- No prompt, output or authorization logging, analytics, database or disk persistence in this service. Inputs are processed in memory; hashes and draft results are kept for up to five minutes to deduplicate request IDs. Host-level operational metadata may still be recorded. The host and OpenAI process message content.
- API inputs are not used for model training by default. `store:false` does not remove abuse-monitoring retention or all provider caching. OpenAI may retain content in abuse logs for up to 30 days, with legal/safety exceptions.
- Single-instance safeguards: two concurrent generations, 20 per minute and 200 attempts per UTC day. **These counters reset on restart and multiply with replicas. They are not a hard account spending limit.** Configure OpenAI project spending controls and host billing controls independently.
- Revoke the phone by rotating `REPLY_PILOT_TOKEN` on the server and redeploying. Re-pair only the intended phone with the new token. Deleting the phone’s local connection alone cannot revoke copied codes. Rotate the OpenAI key separately if compromised.
